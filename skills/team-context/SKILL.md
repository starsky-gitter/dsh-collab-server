# 团队共享上下文

团队里每个人的 AI 都能检索到一个共享的记录库。你的责任是：**在任务收尾时，把这一轮真正可复用的结论留下一条**，而不是把过程倒进去。

## 什么时候提交

- 定位到一个硬件/时序/驱动问题，并知道触发条件和规避方式。
- 做了一个有取舍的设计决定，且理由不是显而易见的。
- 发现某个"常识"在当前板卡/工具链上不成立（踩坑教训）。
- 确认了环境差异：某个版本、某块板、某个 SDK 补丁是必需的。
- 一条路走死了，且下一个人的 AI 很可能再走一遍。

## 什么时候不提交

- 只是改了代码、没有结论（纯实现、重命名、格式化）。
- 结论是通用的、网上随处可查的。
- 内容里有密钥、客户数据、完整日志原文。
- 同一个结论本轮已经提交过。

## 怎么做

1. 先 `team_recall` 用关键词查重；已有同一条就跳过，过期就 `team_review` 标失效，而不是重复写。
2. 没有就 `team_share`，一条只讲一个结论：
   - `title`：症状 + 条件 + 结论，能被搜索到（不要写"CAN 问题"）。
   - `body`：200–600 字，写清现象、适用条件（板卡/芯片/工具链）、怎么验证的。
   - `kind`：fact / decision / failure / env / bench / change。
   - `scope`：board、mcu、toolchain、paths，能填就填，检索靠它过滤。
   - `evidence`：一条具体的证据（串口结果、构建结果、上板现象）。
3. 没有构建或上板证据时保持 `draft`；有证据才设 `verified`。
4. 提交后继续你的收尾工作，不要为了写记录而额外做验证。

## 语气

记录是给另一个工程师的 AI 看的，不是给人看的报告。短、具体、可执行，不带客套。
